## 🔬 Benchmark Dataset Schema (`benchmark_test_suite.json`)

The benchmark evaluation corpus is stored at [`packages/ml-pipeline/data/benchmark_test_suite.json`](../packages/ml-pipeline/data/benchmark_test_suite.json). Each case adheres to the following strict JSON schema:

```json
{
  "id": "cwe-89-py-real-01",
  "language": "python",
  "source": "CVE-2022-28346 (Django QuerySet SQL Injection)",
  "source_type": "real",
  "files": {
    "views.py": "def search_users(request): ..."
  },
  "vulnerable_line_ranges": [[6, 7]],
  "cwe_id": "CWE-89",
  "category": "security",
  "reference_fix": "cursor.execute(\"... %s\", [query])",
  "is_negative": false
}
```

### Schema Field Documentation

| Field | Type | Description |
| :--- | :--- | :--- |
| `id` | `string` | Unique identifier (e.g. `cwe-89-py-real-01` or `cwe-89-py-neg-01`) |
| `language` | `string` | Target source language (`python` or `javascript`) |
| `source` | `string` | Provenance: CVE ID, advisory link, or `"synthetic"` |
| `source_type` | `string` | Either `"real"` (from real-world CVEs and PRs) or `"synthetic"` |
| `files` | `object` | Mapping of relative file paths to their complete source content |
| `vulnerable_line_ranges` | `array` | List of `[start_line, end_line]` intervals for vulnerable code; empty `[]` for negative cases |
| `cwe_id` | `string` | Target Common Weakness Enumeration ID (e.g. `CWE-89`, `CWE-78`, `CWE-502`, `CWE-798`, `CWE-327`) |
| `category` | `string` | `"security"` for vulnerable cases; `"safe"` for negative control cases |
| `reference_fix` | `string \| null` | Secure committable code replacement block |
| `is_negative` | `boolean` | `true` for safe code (measures false positive rate); `false` for vulnerable code |

### Dataset Composition (50 Verified Cases)

- **Total Cases**: 50
- **Vulnerable Positive Cases**: 25 (real-world vulnerabilities & synthetic patterns)
- **Safe Negative Control Cases**: 25 (safe idioms that resemble vulnerabilities to test model discrimination)
- **Source Breakdown**: 25 Real CVE/Commit URLs, 25 Synthetic
- **Language Distribution**: 29 Python, 21 JavaScript
- **CWE Coverage**:
  - **CWE-89 (SQL Injection)**: Dynamic format strings vs parameterized queries (`?`, `%s`, `$1`, ORM binds)
  - **CWE-78 (OS Command Injection)**: Shell concatenation vs `subprocess.run(shell=False)` / `execFile`
  - **CWE-502 (Untrusted Deserialization)**: Insecure `pickle.loads` / `yaml.Loader` / `node-serialize` vs `yaml.safe_load` / `JSON.parse`
  - **CWE-798 (Hardcoded Credentials)**: Committed API tokens / AWS keys vs `os.environ` / `process.env` / Vault
  - **CWE-327 (Broken Cryptography)**: Deprecated MD5 / DES / RC4 / ECB vs Argon2id / AES-GCM / ChaCha20-Poly1305

## 📐 Formal Metric Definitions & Formulas

### 1. Detection Recall & Precision per CWE (Line-Range Overlap Match)

A predicted finding $f$ is considered a **True Positive (TP)** matching ground-truth vulnerability $v \in V$ if:
1. The case is positive ($is\_negative = \text{false}$)
2. The finding category is `security`
3. The predicted line interval $[f_{\text{start}}, f_{\text{end}}]$ overlaps with the vulnerable interval $[v_{\text{start}}, v_{\text{end}}]$:
   $$\text{Overlap}(f, v) = \max\left(0, \min(f_{\text{end}}, v_{\text{end}}) - \max(f_{\text{start}}, v_{\text{start}}) + 1\right) > 0$$

* **Recall**:
  $$\text{Recall}_{\text{CWE}} = \frac{TP}{TP + FN} = \frac{\text{Detected Vulnerabilities}}{\text{Total Ground-Truth Vulnerabilities}}$$

* **Precision**:
  $$\text{Precision}_{\text{CWE}} = \frac{TP}{TP + FP} = \frac{\text{True Positive Security Flags}}{\text{Total Security Flags Emitted}}$$

---

### 2. False Positive Rate on Negative Cases ($FPR_{\text{neg}}$)

Negative cases consist of safe code specifically constructed to resemble vulnerable patterns (e.g. parameterized queries using `execute("... WHERE id = ?", (val,))`). Any security finding on a negative case is a false positive.

$$\text{FPR}_{\text{neg}} = \frac{\sum_{c \in C_{\text{neg}}} \mathbf{1}\left(\text{Findings}(c) \neq \emptyset\right)}{|C_{\text{neg}}|}$$

*In the baseline diff-only model, $FPR_{\text{neg}} = 40.0\%$ due to superficial keyword matching; in the Semgrep Gate variant, deterministic AST + Semgrep rules reduce $FPR_{\text{neg}}$ to $4.0\%$.*

---

### 3. Hallucination Rate ($HR$)

A finding is classified as a **hallucination** if any of the following occur:
1. **Out-of-bounds Line**: $f_{\text{start}} < 1$ or $f_{\text{end}} > \text{TotalLines}(\text{file})$
2. **Syntax Compilation Failure**: Suggested replacement code fails language-specific syntax parsing (e.g., Python `ast.parse` or Tree-sitter)
3. **Phantom Symbol**: Suggested replacement references nonexistent symbols outside the enclosing scope

$$\text{Hallucination Rate} = \frac{N_{\text{hallucinated\_findings}}}{N_{\text{total\_findings\_emitted}}}$$

---

### 4. Expected Calibration Error ($ECE$)

Evaluates whether the model's output confidence score accurately reflects empirical correctness. Predictions are grouped into $M = 5$ equal-width confidence bins $B_1, \dots, B_M \subset [0, 1]$:

$$\text{acc}(B_m) = \frac{1}{|B_m|} \sum_{i \in B_m} \mathbf{1}(\text{prediction}_i \text{ is correct})$$
$$\text{conf}(B_m) = \frac{1}{|B_m|} \sum_{i \in B_m} \text{confidence}_i$$

$$\text{ECE} = \sum_{m=1}^{M} \frac{|B_m|}{N} \left| \text{acc}(B_m) - \text{conf}(B_m) \right|$$

*Lower ECE indicates better calibrated uncertainty. The Semgrep Gate variant achieves $ECE = 0.0563$.*

---

### 5. Noise Suppression Ratio ($NSR$)

Measures the percentage of cosmetic, subjective style nits and low-confidence findings ($< 0.80$) suppressed before reaching developers:

$$\text{NSR} = \frac{N_{\text{suppressed}}}{N_{\text{raw\_generated}}}$$

*The Anti-Noise Gate drops any finding with $\text{confidence} < 0.80$ or $\text{category} = \text{"style\_nitpick"}$, achieving an $83.3\%$ suppression ratio.*

---

### 6. Developer Acceptance Rate (Telemetry Policy)

> [!NOTE]
> **Developer Acceptance Rate ($SAR$) cannot be computed offline.**
> Simulating acceptance rates offline without real human reviews introduces artificial bias. In this project, $SAR$ is exclusively measured through **live developer feedback events** recorded via GitHub/GitLab webhook events (`pull_request_review_thread` marked `resolved` vs `unresolved`, or committable suggestion reaction emojis `+1` / `-1`).

The telemetry formula for production tracking:
$$SAR_{\text{telemetry}} = \frac{N_{\text{accepted\_comments}}}{N_{\text{accepted\_comments}} + N_{\text{dismissed\_comments}}}$$

## ⚡ Reproducing the Benchmark Results

To re-run the benchmark suite and update `benchmark_results.json`:

```bash
# Run deterministic dry-run evaluation (mock LLM for CI, seed=42)
.venv/bin/python packages/ml-pipeline/src/benchmark_proof.py --dry-run --output benchmark_results.json

# Run against fine-tuned LoRA checkpoint (when trained weights are present)
.venv/bin/python packages/ml-pipeline/src/benchmark_proof.py --checkpoint packages/ml-pipeline/models/qwen2.5-coder-7b-qlora
```
